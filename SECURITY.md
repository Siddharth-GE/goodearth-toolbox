# SECURITY.md — the boundary rules

Auth, permissions, money, the line chain and the cross-tool contracts. CLAUDE.md carries each rule's one-line form; this file is the mechanics and the why. Read it before touching any of this — every rule here either broke once or was designed against a break.

## Auth and permissions

- **The app grant IS the permission boundary.** Every query and action calls `requireTool("<href>")` (`lib/auth/access.ts`) first. Sidebar visibility is cosmetic, and so are its teams (`0114`): readable by every signed-in person, written by admins, read by no policy. Admins get everything. Grants are per-user (`user_apps`) + role bundles (`role_apps`), unioned per request, enforced in the database by `has_app()`.
- **In a tool the founder makes scoped, the grant opens the tool and each row decides the rest** (`0122`). Assigned work alone does not make a tool scoped — Design Management assigns people and actions and stays open to its whole grant, by the founder's choice (`0126`). A scoped tool is flagged `scoped` in `lib/tools.ts`, and its own migration narrows each of its policies in place to the grant _and_ "mine" — still one policy per command. An admin or the tool's **team lead** counts every row as theirs: `is_lead(slug)`, ticked per person beside the grant in Settings, built from `has_app()` and `is_admin()` (so it carries `session_is_verified()` without redefining either), and nothing without the grant. What "mine" means is each tool's own — the flag alone switches nothing on. Three things bite: a policy that asks about another table goes through a `security definer` helper, or two tables' policies recurse; **Postgres checks an updated row against the SELECT policy too**, so a policy over the row's own columns refuses a hand-over that takes the row out of the hander's sight — ask by id (the helper reads the row as it was) and give the row's own columns a first branch, so an insert that asks for its row back still passes; and **every view over a scoped table bypasses all of it**, so its `WHERE` must not admit the scoped grant. Client Relations is the one scoped tool — _Assigned work_ below.
- **Signing in is password → emailed 6-digit code** (10 minutes; a 30-day trusted device skips the code, never the password), or Google for an email that already has an account; public signups are off. Both steps are rate-limited in the database: 10 wrong in 10 minutes locks for 10. The enforcing half is `auth_verified_sessions` (`0062`): since `0063`, `has_app()` and `is_admin()` answer **false for any session without its row**, so a session minted from the auth API with a stolen password reaches nothing gated. So **redefining `has_app()` or `is_admin()` must carry `session_is_verified()` forward**, and only the server ever writes `auth_verified_sessions` — a self-service marking function would let the session being screened pass itself.
- **In the phone app, Google returns to the app's own address**, `com.kaadalgroup.toolbox://auth/callback` (`lib/native/app.ts`, `mobile/PLAN.md`), and the app finishes on `/auth/callback` in its web view. Any app can claim that address, so the return carries nothing but the code, and the code is worth nothing without the PKCE cookie in our web view. The user agent's mark only chooses the return address, which Supabase's allow-list still gates: a faked mark breaks only the faker's own sign-in.
- **The phone app can keep a person's password, locked to their fingerprint or face** (`mobile/PLAN.md`). It adds no way in: the app signs in through the ordinary password path, so the lockout, the switched-off check and the emailed code all still apply. The Keystore key decrypts only after a strong biometric and is retired when a fingerprint is added; only the app's own `/login` may ask for it, and Capacitor's bridge reaches only our origin's main frame, so a Dexter deck cannot. Anyone whose fingerprint is on that phone can use it, so a shared site phone should not keep one.
- **Every unauthenticated route goes in `PUBLIC_PATHS`** (`lib/supabase/proxy.ts`) as an **exact string** — a missing entry 302s to /login before the route runs; a prefix would make neighbouring routes silently public. **`/deck/` is the one prefix** (`PUBLIC_PREFIXES`): Dexter's viewer serves assets relative to itself, and its gate is the token inside the route. A second prefix needs the same argument written here first.
- **All database access is server-side.** No browser Supabase client exists — do not add one. So the session cookies are `httpOnly` (`lib/supabase/cookie-options.ts`, used by both server clients): page script can never read them.
- **Tools use the RLS-scoped client** (`lib/supabase/server.ts`), never the admin client. The sanctioned exceptions, each for want of a session: `inviteUser` (auth-admin API); the sign-in flow's `lib/auth/rate-limit.ts` and `markSessionVerified` (deny-all tables); the OAuth callback's delete of a signup-leak account; the keep-alive's one-row read (a cron, gated by `CRON_SECRET`); the Google Chat door's `lib/google-chat/`; **push notifications'** `lib/push/send.ts` (_Push notifications_ below); and **Dexter's public door**, the one inside a tool (reads, and the one write _Dexter's public door_ below describes).
- **RLS on for every table, always.** A new table without policies is a bug.
- **Every read asks for the second factor** (`0129`). A read policy is never `using (true)`: the floor is `session_is_verified()`, so a password-only session reads nothing. `profiles` also admits a person's own row (`or id = auth.uid()`), because the sign-in flow reads it to refuse a switched-off account before the code is done. A new table copies the floor. **Every check in a policy is wrapped** — `(select session_is_verified())`, `(select has_app('/x'))`, `(select auth.uid())` — so it runs once per query, not once per row (`0139`, BUGCATCHER #23); `db:check-policies` refuses a bare one.
- **anon can call nothing and read no view** (`0129`, and the default privileges it set, so a new function or view starts that way). pg_trgm's own functions are the exception: they read no data and belong to Supabase's admin role.
- **Definers that check no grant, on purpose:** `has_app`, `is_admin`, `is_lead` and `session_is_verified` are the checks themselves; `profile_is_active` answers only whether an account is switched on; `pusher_current_stage` and `stock_qty_on_hand` return one figure that every signed-in person may already see; `claim_push_device` gives the caller the one phone row with that token (_Push notifications_). Each sets `search_path`. `npm run db:check-policies` names any other.
- **A view is a read surface.** Views are owned by `postgres` and bypass RLS, and Supabase grants writes on every new relation, so a view left writable is an RLS bypass. Every new view revokes insert, update, delete, truncate from **`anon, authenticated`** (naming them — `from public` does not), and every new function revokes execute from `public, anon`, in the same migration. `drop view` restores the default grants every time. `npm run db:check-views` fails a pull request on a writable view (BUGCATCHER #3).
- **Every `security definer` function checks `has_app(...)` or `is_admin()` in its own body** — that check is its whole boundary — unless no client role may execute it (revoked from `anon` and `authenticated`, reached only by a trigger), in which case the grant is. `security definer` changes the role, not `auth.uid()`, so a check inside a function reached from a cross-tool trigger uses `pg_trigger_depth() = 0` to tell a direct call from the trigger (BUGCATCHER #11).
- **Two functions read other people's grants: `client_relations_team()`** (`0120`) **and `design_team()`** (`0126`). A member cannot read anyone else's `user_apps` row, but each tool must offer its team as owners; so each `security definer` checks its own grant (`has_app('/client-relations')`, `has_app('/design-management')`) in its body and hands back the id and name of active holders of that one grant — never an email, never which grant, never anyone else. Client Relations leaves admins out (they are its managers) and checks every owner in its writes; Design Management lists an admin only if they hold the grant too, and its guards check every person put on a stage and every action's owner in the database.
- **Actions return `ActionState`** (`lib/action-state.ts`), never throw. Queries may throw — a failed read has no partial answer worth showing.
- **Never seed a real default credential** — a seed is a fixture in development and a credential in production.

## The Google Chat door

The app's one unauthenticated POST (`app/api/google-chat/route.ts`). Everything under `lib/google-chat/` follows from having **no browser session**; its plan is `lib/google-chat/PLAN.md`.

- **The lock is the token, and its email claim is load-bearing.** `verify.ts` checks each request's Google ID token with `node:crypto`: RS256, issuer `accounts.google.com`, audience `GOOGLE_CHAT_AUDIENCE`, **and** `email` = `service-<GOOGLE_CHAT_PROJECT_NUMBER>@gcp-sa-gsuiteaddons.iam.gserviceaccount.com`. Any Google service account can mint a token for our audience; only the email says it is our Chat app. The body is not read until the token passes. `route.ts` holds only this; everything after lives in `dispatch.ts`.
- **Who typed is Google's word, mapped to one account.** `identity.ts` maps the sender email to an active account holding `/relay`, and refuses anyone else in five fixed sentences that never reveal who exists.
- **Reads go through the admin client on Relay's tables** — `pusher_chain_state`, its legs, events, activities and departments, the trail sets, and names from `profiles`, `projects`, `units` — the same everyone-signed-in-sees-every-trail view Relay reads. `google_chat_spaces` (`0094`) is the door's own deny-all table.
- **Writes are made as the person, never as the system.** `act-as.ts` is the only place that mints a session for somebody else — admin `generateLink` → `verifyOtp` → the verified-session row → the write → **always** delete the row and revoke the session (`"local"`, never `"global"`). `has_app('/relay')` and Relay's guard stay the boundary; every event carries the person's `actor_id`. It has one caller and must never grow a second.
- **The app's own credential may do one thing.** `GOOGLE_CHAT_SERVICE_ACCOUNT_KEY` lets `outbound.ts` rewrite a card the app itself posted, after a press. It never touches the database, mints a session or moves a baton. Unset, the door behaves as before.
- **Nothing logs message text, an email, a token or a session id.** No replay table yet — Google's token `exp` and the single-use magic link cover it; a deferral, not a decision.

## Push notifications

A phone app tells a person when work reaches them (`lib/push/`, `0130`). The rules:

- **A person's phones are theirs alone.** `push_devices` has one read and one delete policy, both the caller's own rows with `session_is_verified()`, and no insert or update policy. A phone is recorded only through `claim_push_device()`, a definer that hands the row with that token to the caller and nobody else: a shared site phone follows whoever signed in last. Sign-out deletes the phone's row.
- **Sending to someone else reads their phones through the admin client**, in `lib/push/send.ts` alone: it reads `push_devices` for the people it is given (active accounts only) and deletes only a token Firebase calls gone. Who is told is decided by the calling action, from the row it has just written as the person. A tool never reads `push_devices` itself.
- **After the write, never inside it.** `notifyAfter()` runs once the response has gone (`after()`), never throws, and never fails or slows the write. The actor is never told about their own act.
- **The lock screen shows the words**, so a notification carries no money and no free text: an indent's reference, a villa's and a stage's or activity's names. A tap opens a path on our own site only (`safePushPath`).
- **The Firebase key** (`FIREBASE_SERVICE_ACCOUNT_KEY`) is asked only for `firebase.messaging`, lives in Vercel's settings, and is never logged; unset, nothing is sent. `google-services.json` is copied into the app at build and never committed.

## Design Management reads a WorkDrive folder

A revision's drawings are a Zoho WorkDrive "anyone can view" share link (`0124`), and the server reads the shared folder's list the way its public page does (`lib/design-management/workdrive.ts`) — no Zoho key exists, and none is needed.

- **The server fetches only Zoho's share host, at an address it rebuilt.** `parseWorkDriveLink` takes the id out of what was pasted and builds `https://workdrive.zohoexternal.com/external/<id>`; the pasted text is never fetched, so a typed address cannot make the server call anywhere else. The database checks the stored link's shape too.
- **Names, sizes and times only — never a file.** The viewing cookies Zoho hands any visitor live for one read and are never stored or logged; nor is Zoho's answer.
- **The kept list has the uploaded sheets' reach**: one SELECT policy, the design team or `/supervisors` once released; writes `/design-management`, while draft only (the draft-only trigger).

## Dexter's public door

A client opens `/deck/<token>/index.html` and sees an uploaded presentation.

- **The token is the whole gate, checked for shape before anything is read** — 22 base64url characters, pinned by `0095`'s CHECK and the route's pattern. A switched-off deck answers exactly like a token that never existed; "New link" kills the old one.
- **Admin client: reads, and one write.** No `anon` policy exists on `dexter_projects`, `dexter_decks`, `dexter_answers` or the bucket (`0095` and `0100` assert it), so the public side can be widened only by editing this route. `safeDeckPath` refuses traversal and joins every path under `decks/<id>/`.
- **The write is `POST /deck/<token>/.state`** (`0100`): an upsert of the deck's own `dexter_answers` row — the deck id comes from the token lookup, never from the request, so no other row is reachable — after the body has passed `parseAnswers` (`lib/dexter/answers.ts`, pure and tested: 64 KB, 200 flat fields of text, tick or list). `submitted_at` moves only from null to now there; clearing answers is a staff action. **Nobody signed in can insert or update that table** — `0100` creates no policy for it and asserts none exists; `has_app('/dexter')` reads and deletes. The three reserved names (`.dexter.js`, `.state`, `.preview.png`) begin with a dot because `planZip` drops dot-prefixed paths at upload, so no deck file can ever be shadowed.
- **Every HTML response carries our link-preview tags** — inert `<meta>` elements added to the response by `lib/dexter/preview.ts` (pure and tested); the stored file is never changed and nothing that runs is added. The title is escaped to ASCII, and a file with a UTF-16 byte-order mark is served untouched. `.preview.png` is the picture: gated by the token like every other path, its colour a validated six-digit parameter, its generator loaded lazily.
- **Only the `.state` responses carry `Access-Control-Allow-Origin: *`.** The sandboxed page is an opaque origin and could not read our reply without it; `*` forbids credentials, and none exist on either side — the browser sends no cookie from an opaque origin and the route reads none. The page and its assets never carry the header.
- **The page is untrusted HTML on our own origin**, so every deck file, whatever its type, carries `Content-Security-Policy: sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals` (`lib/dexter/headers.ts`) — **never `allow-same-origin`**, which would hand an uploaded deck the viewer's session. Never narrow it to a list of types (BUGCATCHER #21); `nosniff` and a content type from the extension stop disguised files.
- No view counting (a write on every open, not on the client's own action), passwords or expiry, by decision.

## The line chain

Design flows to payment through the database, never through shared code. The two files deciding what carries forward (`lib/budgets/carry-forward.ts`, `lib/indents/pull-rules.ts`) are pure and import nothing.

| Hop                | Anchor                                                                        |
| ------------------ | ----------------------------------------------------------------------------- |
| selection → budget | composite FK `(selection_id, line_key)`                                       |
| budget → indent    | composite FK `(budget_id, line_key)`                                          |
| indent → PO        | FK `purchase_order_lines.indent_line_id`, required on every new line (`0113`) |
| PO → receipt       | FK `goods_receipt_lines.po_line_id`, not null                                 |
| receipt → issue    | `stock_batch_movements.receipt_line_id` (`0108`)                              |
| PO → bill          | FK `bills.po_id`; per line `bill_lines.po_line_id`                            |
| labour log → bill  | `labour_logs.bill_id`, `bill_lines.labour_log_id`                             |
| bill → paid        | `bill_payments.bill_id`, `advance_recoveries`                                 |

- **Anchor on stable ids or the composite FK — never a bare `line_key`.**
- **Deletion is refused, not cascaded.** Issued revisions are immutable (`selection_lines_draft_only`) and the FKs restrict. Drift is flagged instead: `classifyDesignDrift` marks changed lines, `getDownstreamImpact` shows the indents and POs a change would hit.

## Money stays confined

Indents carries no money, and neither does a supervisor's phone — labour logs hold heads and quantities, and the billing team prices them in Bills. PO money is RLS-gated to `/purchase-orders`; everyone else reads the money-free views (`po_facts`, `po_line_facts`, `approved_budgets(_lines)`, `bill_facts`, `work_unit_facts`, `batch_on_hand`). **Thirteen views carry money** (`money: true` in `scripts/view-manifest.ts`), each gated in its own `WHERE` except `budget_report_lines`, which inherits RLS; the bullets below name them. Five are windows between tools: `po_billing_totals` (ordered and billed totals, PO charges included since `0133`) and `po_line_billing_facts` (`0106` — each PO line's rate, GST, discount and charges, so a material bill pre-fills from its PO) are the two sanctioned windows between POs and bills, both `/purchase-orders` or `/bills`; `work_labour_rate_facts` (`0105` — the rate book's labour rate per work, for a work order) is `/bills` or `/estimator`, and is never widened to `/supervisors`; `work_order_line_billing_facts` (`0136` — each work order line's value and what is billed against it, for stage billing) is `/bills` or `/reporter`; and `villa_cost_facts` (`0136` — per villa and work, the official estimate against what was committed and spent, before GST) is `/estimator`, `/bills` or `/reporter`, by the founder's decision 2026-10-22.

- **Bills' money is `/bills` on every table** — `bills`, `bill_lines` (`0106`), work order lines `labour_contract_lines` (`0105`), and the payment tables `bill_payments`, `contractor_advances`, `advance_recoveries`, `cash_requests`, `cash_request_items` (`0107`), each with one SELECT policy of `has_app('/bills') or has_app('/reporter')`. `bill_payments`, `contractor_advances` and `advance_recoveries` have no update or delete policy at all. Work order templates carry no rates.
- **Inventory carries rates for `/inventory` holders only** (founder 2026-10-08, reversing "no money in Inventory"), in their own table: `goods_receipt_line_rates` (`0108`) — SELECT `/inventory`, `/purchase-orders`, `/bills` or `/reporter`; update `/inventory`; no insert policy. A store-keeper cannot read PO tables, so the PO's rate arrives through `goods_receipt_lines_copy_rate`, a trigger-only definer with execute revoked — the one path PO money takes into Inventory. The stock tables (`goods_receipts(_lines)`, `stock_issues(_lines)`, adjustments, `stock_batch_movements`, `batch_on_hand`) stay money-free and open to every signed-in person; an issue's value is worked out from its batches' rates on screen, never stored.
- **Two named exceptions, by founder decision.** `/reporter` reads PO, bill (lines and payments included), budget, margin and store-rate money (`0055`, then each new money table's own policy) by widening each table's one SELECT qual to `has_app('/x') or has_app('/reporter')`. `/financial-management` reads client money, bill money and plan targets (`0058`) through owner views gated in their own `WHERE`, plus `bill_money_facts`. Both grants carry an amber `grantWarning` in `lib/tools.ts` — keep it; since `0117` it names Birdwing's money too. `budget_report_lines` is the one `security_invoker` view, so it inherits RLS. `crm_milestone_facts`/`crm_receipt_facts` omit the CRM's prose (details, notes, bottlenecks), which is its stronger secret, and since `0123` admit only `/reporter` and `/financial-management` — never `/client-relations`, whose members see only their own plots' money.
- **`/estimator` is a self-contained money surface** (`0074`): every table gated on SELECT too. Its one cross-tool money read is `villa_cost_facts` (`0136`, gated above): committed and actual money per villa, by the founder's decision 2026-10-22. Other tools see it only through five views: `estimate_takeoff_facts` and `estimate_work_facts` (`0137`, each work's quantity), the rate-free windows Indents, Inventory and Supervisors read; `work_unit_facts` (`0104`), each work's unit and nothing else, open to signed-in; and `work_labour_rate_facts` and `villa_cost_facts`, gated above — the estimate's figures reach `/bills` through that one view. The material rate is `items.indicative_price`, visible to all; only what the Estimator computes from it is gated. Since `0103` that rate rises when a PO pays more (a cross-tool write, below) — a rate per bag is not the secret; which vendor, which PO and the old price are, and they live in `item_price_changes`, gated to `/masters` or `/purchase-orders`.
- **Birdwing's money stays in its two tools** (`0115`–`0117`). Stays — guests, stays, charges, invoices, receipts, cross-charges — is `/birdwing` on every table; Books — expenses, attendance, pay rules, salaries — is `/birdwing-books`. Neither reads the other's tables: Books sees occupancy only through `birdwing_occupancy_facts` (rooms and guests per day, no name, no rupee). `/financial-management` and `/reporter` read Birdwing through three owner views gated in their own `WHERE` — `birdwing_stay_facts`, `birdwing_expense_facts`, `birdwing_month_facts` — which carry a guest's name and **never a phone, email or ID** (`0117` asserts it). The tables' quals were deliberately not widened to those grants: a wider qual would hand over the phone numbers too. Every Birdwing function runs as the caller; a guest's ID document sits in the private `birdwing-stays` bucket and a bill in `birdwing-books`, each served through an RLS lookup.
- **`vendor_payment_details` is the one gated Masters table** (`0089`/`0090`) — bank details: SELECT needs `/masters`, `/purchase-orders` or `/bills`, writes need `/masters`.
- **Never add a money column to a fact view.** Its `WHERE` and column list are the boundary; no policy stands behind them. `scripts/view-manifest.ts` pins every view's columns, guards, barrier/invoker flags and absent write grants, and `npm run db:check-views` runs on every pull request. Changing a view means changing its manifest row in the same commit, with a sentence saying why.
- **Never add a second SELECT policy to a gated table** — permissive policies OR together and the second is invisible. Widen the existing qual.
- **Redefining a CRM or plan facts view must carry its `WHERE` forward** — `crm_milestone_facts` and `crm_receipt_facts` two-way (`0123`), `business_plan_target_facts` three-way (`0058`). Re-running `0056`–`0058` as they are either strips Financial Management's access or hands every Client Relations member every plot's money.

## Assigned work — Client Relations (`0123`)

The one scoped tool (_Auth and permissions_ above). Its rules are the founder's (Client Relations' `PLAN.md`, decision 6); these are the mechanics.

- **A plot** — `client_engagements`, and with it `client_payment_milestones` and `client_receipts` — is seen by its Construction and Interior owners (`crm_owner_id`, `kaadal_owner_id`), by whoever owns or set an open action on it, and by admins and leads: `crm_sees_plot()`. **An action**, by its owner, its setter and its plot's owners: the row's own columns first, then `crm_sees_action()` by id. Admins and leads see every row.
- **Putting an action on a plot needs the plot in sight** (`crm_may_place_action()`, insert and update), so nobody makes a plot visible to themselves by hanging an action on it. The plot it is already on stays allowed, so a setter can reopen an action whose plot they saw only while it was open.
- **Handing on is allowed, and the hander loses sight** — the update and its SELECT check read the plot or action as it was (_Auth and permissions_).
- **The four helpers are `security definer`** so the two tables' policies can ask about each other without recursing; each answers only about the caller, every branch through `has_app('/client-relations')` or `is_lead()`, execute revoked from `public, anon`.
- **The buyer doors stop at what the caller sees**: `crm_assign_unit` and `crm_release_unit` refuse a plot with a buyer the caller cannot see. An unsold plot can be sold by anyone on the team, and if nobody owns it, it goes to the client's handler or else the seller — so it does not leave their sight as they sell it.
- **The client list is not scoped.** `clients` is Masters' shared surface, readable by every signed-in person, prospects' contact details and notes included. The Clients screen lists a member's own (`clientScope` in `lib/client-relations/queries.ts`) as a convenience, not a boundary.
- **No view admits `/client-relations`** — the two CRM facts views are Reporter's and Financial Management's (_Money stays confined_). A new view over these tables either keeps it out or carries the same "mine".
- **One owner per side** (`0125`): every open step on a plot's side is that side's owner's. Two `security definer` triggers hold it — `client_actions_follow_side` refuses a step on a side with no owner or for anyone else, and `client_engagements_hand_over` moves a side's open steps with its owner and refuses leaving a side with open steps to nobody. Execute is revoked from every client role, so the grant is their boundary; they move only `owner_id` on steps of the plot being written, never a policy's answer. A session with no `auth.uid()` (scripts) is never refused and fills a blank side from its step.

## Cross-tool reads and writes

Reads: STATUS.md's contract table, which IS the contract; the import rule is CLAUDE.md's. **No tool's code writes another tool's table**, except these, each deliberate:

- `indent_approvers` / `bill_approvers` are Settings'-owned, though they live in Indents' and Bills' migrations.
- The `projects_seed_schedule` trigger (`0045`): creating a project in Masters seeds Relay's schedule — declared by Relay's migration, so the coupling points the right way.
- Client Relations writes Masters (`0050`, `0051`) through two column-narrow definer functions and the `units_seed_engagement` trigger.
- Directory's `profiles_seed_staff_details` trigger (`0060`) gives every new account a blank card inside Settings' `inviteUser` — give `staff_details` a `not null` column without a default and `inviteUser` breaks. Plus `updateMyName`: a person's own `profiles.full_name`.
- Inventory resolves Supervisors' `issue_requests` (`0084`) — fulfil stamps `fulfilled_issue_id`, decline records a reason; `issue_requests_guard()` lets that side move only `requested → fulfilled/declined`.
- Bills stamps Supervisors' `labour_logs.bill_id` (`0104`/`0106`) — only inside `send_labour_logs_to_bill()` and `delete_recorded_bill()`, definer functions that check `/bills` first, behind a transaction-local flag only they raise; `labour_logs_billed_guard()` lets that column move and nothing else, and freezes a billed entry.
- The Estimator answers Indents' `indent_lines` (`0113`) — approve or refuse a line outside the estimate — only inside `decide_indent_line()`, a definer that checks `/estimator` first (it is only ever called directly, so `auth.uid()` is the estimator), that the indent is submitted and that the line has no anchor, behind a transaction-local flag only it raises; `indent_lines_draft_only` then lets the four answer columns move and nothing else. `indents_guard` refuses approval until every such line is approved.
- Issuing a PO raises Masters' `items.indicative_price` (`0103`) when the PO paid more — a trigger-only definer, execute revoked from every client role, never lowering; `item_price_changes` logs it, gated to `/masters` or `/purchase-orders`.
- Selections proposes catalogue items: the "items proposable by selections app" INSERT policy admits `/selections` for `is_provisional` rows only, through the invoker function `create_item_request`; Masters approves or merges them later.

**A cross-tool trigger or definer function not listed here is what nobody finds until it misfires.** Redefining `pusher_chain_state`, the most-read view: `relay/PLAN.md` first.

## Reads

- **PostgREST caps a select at 1,000 rows.** Anything needing completeness goes through `fetchAll` (`lib/supabase/fetch-all.ts`), which throws if a page fails. Lists show "N of M" from a real count, never `rows.length`.
- **Always check `error`, not just `data`.** An empty result and a failed read mean opposite things; conflating them has destroyed priced budget lines, cleared drift warnings and re-opened double-buying.
- **An embed through a table with two FKs to the same target names the key** (BUGCATCHER #2).
